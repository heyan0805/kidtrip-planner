# kidtrip-backend · 童行后端

「童行 · 带娃旅游规划器」的后端。**一句话职责：把"用户的模糊出行意愿"变成"一份可执行、可追溯的行程"**，
中间所有的事实（景点、酒店、城际车次、经纬度）都来自飞猪，一格都不许模型自己编。

- Spring Boot **4.1.1** · Java **21** · LangChain4j **1.18.1** · DeepSeek（`deepseek-chat`）
- 端口 **8003**（参照工程是 8002，两个可以同时跑）
- 66 个源文件 / 9731 行 · 26 个测试类 / **369** 个用例

> 前端说明见 [`../frontend/README.md`](../frontend/README.md)；
> 想先看整体架构和产品原则，读仓库根的 [`../README.md`](../README.md)。

---

## 1. 它在这条链路上的位置

```
用户对话 ──► 画像(params)
                │
                ▼
       ┌────────────────────┐
       │  检索层 retrieval    │  调飞猪 CLI 拿真实候选（景点/酒店/城际车次）
       │  限流 + 缓存         │  ← 坐标、价格、地址、车次时刻，都是这一层拿到的
       └─────────┬──────────┘
                 ▼
       ┌────────────────────┐
       │  候选层 candidate    │  规范化 + 去重
       │  规则层 rule         │  白名单筛选（价格上限、类别、时长上限）
       └─────────┬──────────┘
                 ▼
       ┌────────────────────┐
       │  大模型 llm          │  模型**只能从候选里挑编号**，不能自己造名字
       │  三个 Composer       │  名称/价格/地址/链接/坐标由后端按编号回填
       └─────────┬──────────┘
                 ▼
       ┌────────────────────┐
       │  编排层 plan         │  装配 + 兜底校验（首末日冲突、距离跨度、车次时段）
       │                    │  冲突不拦行程，只写进 warnings 让界面说人话
       └─────────┬──────────┘
                 ▼
              行程(TravelPlan) + 注意事项(warnings) + 备选池(spotPool)
```

**核心不变量：模型负责措辞，代码负责事实。**
"编一个不存在的景点"在这套结构里做不到 —— 模型输出的是 `C3` 这样的编号，
名称、票价、地址、购票链接、经纬度全部由后端按编号查表回填。

## 2. 快速开始

### 2.1 前置条件

| 需要 | 说明 |
|---|---|
| JDK 21 | `java -version` 应显示 21 |
| Maven | 本机离线跑会缺插件依赖，**第一次要联网**补齐 |
| Node.js | 后端会 `ProcessBuilder` 起 `node` 子进程去跑飞猪 CLI |
| 飞猪 CLI | `npm i -g @fly-ai/flyai-cli`，装完用 `npm root -g` 找它的位置 |
| 飞猪凭据 | `~/.flyai/config.json` 里要有 `FLYAI_API_KEY`，同目录还有 `device-id` |
| DeepSeek Key | 自己去申请，配到环境变量里 |

> ⚠️ **飞猪 CLI 需要凭据才能查**，凭据放在 `~/.flyai/config.json`（`FLYAI_API_KEY`），
> 同目录还有一个 `device-id`。换机器 / 换容器部署时这两个要一起带过去 ——
> 换一个全新的 `device-id` 会不会被上游风控拦下，**没验证过**。

### 2.2 两个必须配的环境变量

**没有默认值，且故意不留默认值**（写进仓库就等于泄露）：

```bash
# 飞猪 CLI 的 bundle 绝对路径（注意指向 dist/flyai-bundle.cjs，不是那个 flyai.cmd）
# 找不到它：npm root -g
export FLYAI_CLI_PATH="$(npm root -g)/@fly-ai/flyai-cli/dist/flyai-bundle.cjs"

# DeepSeek 密钥
export DEEPSEEK_API_KEY=sk-xxxxxxxx
```

Windows（CMD）：`set FLYAI_CLI_PATH=...` / `set DEEPSEEK_API_KEY=sk-xxx`

两个都缺一不可：缺 `DEEPSEEK_API_KEY` **启动就失败**（不是用到才失败）——
一个连模型都连不上的规划服务让它起来只会骗人。

### 2.3 跑起来

```bash
cd backend
mvn spring-boot:run
```

若报 `Port 52562 was already in use`：环境里存在 `SERVER__PORT` 变量，
Spring Boot 的优先级是「命令行参数 > 环境变量 > 配置文件」，它会**悄悄盖掉**这里的 8003。
绕开：

```bash
unset SERVER__PORT && mvn spring-boot:run
```

### 2.4 先确认它活着

```bash
curl -s http://localhost:8003/api/health
# {"code":0,"message":"ok","data":{"status":"up","java":"21.x.x","time":"..."}}
```

## 3. 接口一览

全部返回统一信封（见第 4 节）。**HTTP 状态码恒为 200**，成败看 `code`。

| 方法 | 路径 | 作用 | 请求体 |
|---|---|---|---|
| GET | `/api/health` | 服务活着吗 | — |
| POST | `/api/plan/chat` | 对话，一轮轮把画像攒出来 | `{ messages, currentParams }` |
| POST | `/api/plan/generate` | 拿画像去查、去排，产出行程 | `{ params, retrieval?, maxTicketPriceYuan? }` |
| GET | `/api/plan/progress/{runId}` | 这一次生成走到第几步了（前端每秒轮询） | — |
| POST | `/api/retrieval/pool` | 给一个"期望"，拿回可追溯的候选池 | `{ city, startDate, days, wantedCategories, keywords, needHotel, maxTicketPriceYuan }` |
| GET | `/api/flyai/probe/poi` | **探针**：看飞猪原样吐了什么 | `?city=&category=&keyword=` |
| GET | `/api/flyai/probe/hotel` | **探针**：同上，酒店 | `?city=&poiName=&checkIn=&checkOut=` |

两个探针接口不做任何清洗、不筛选、不缓存，并且**会回显真实命令**。
它们的存在是为了在出问题时能证明「飞猪给的就是这样」，与"我们没把它改坏"分开归因。

`/plan/progress/{runId}` 的 `runId` 由调用方自己生成，从 **请求头 `X-Run-Id`** 带进来 ——
刻意**不进请求体**：那句旁路信息不该混进被契约测试和前端类型两头钉着的 `PlanGenerateRequest`。
不带这个头照样能生成（老调用方零改动），只是没有进度可看。

**`/chat` 和 `/generate` 是前半段和后半段**，不是两个独立功能：
chat 的产物 `params` 正好是 generate 的入参，前端原样递过去即可，不用做任何转换。

实测耗时（这是架构的真实成本，不是调参能消掉的）：

| 接口 | 耗时 |
|---|---|
| `/chat` | 约 5~15 秒（一次模型调用） |
| `/generate` | 约 25~60 秒（检索 2~10s + 规划检索条件 10~20s + 排行程 10~30s） |

## 4. 统一响应约定与错误码

```json
{ "code": 0, "message": "ok", "data": { } }
```

`code = 0` 成功；非 0 时 **`message` 会被前端直接显示给用户**，
所以它必须是给人看的话，不能是 `NullPointerException at line 88`。

| code | 含义 | 用户该做什么 |
|---|---|---|
| `0` | 成功 | — |
| `2001` | 飞猪查询失败 | 多半是城市/条件太窄，改条件 |
| `4000` | 入参不合法 / 请求体读不出来 | 看自己发的东西，一次修好 |
| `5001` | 大模型调用失败 | 再点一次生成 |
| `5000` | 未预期错误 | 稍后重试 |

**错误码的用途不是分类，是让调用方知道该怎么办** ——
2001 和 5001 之所以不复用同一个码，就因为它们的下一步动作不一样。

这个约定的代价要说清楚：网关看状态码永远 200，真实错误率得从响应体里挖；
浏览器 `res.ok` 永远 true。要改的话是**三处一起改**：这里的约定、`ApiResult`、以及前端 `http.ts`。

## 5. 代码结构

按「变化的原因」分包，不按「文件类型」。

| 包 | 职责 | 什么时候会改 |
|---|---|---|
| `common` | `ApiResult` 信封、全局异常出口、JSON 工具 | 改响应约定时 |
| `health` | `/api/health` | 几乎不变 |
| `flyai` | 飞猪 CLI 接入：进程启动、参数拼装、原始 DTO（`raw/`）、城市名校验 | 飞猪 CLI 参数变了 |
| `candidate` | 原始数据 → 干净候选（规范化、去重、坐标） | 上游字段变了 |
| `retrieval` | 检索编排：限流闸门、缓存、城际班次挑选（火车 / 机票两种载体）、候选池 | 检索策略变了 |
| `rule` | 白名单规则与 `RuleChecker` | 产品约束变了 |
| `llm` | 三个 Composer（对话 / 规划检索条件 / 排行程）+ 模型配置 | prompt 变了 |
| `plan` | 编排层 + **契约镜像**（对前端的 DTO 全在这里）+ persona 的闭集与闸门 | 接口契约变了 |

`plan` 包里的 `TravelPlan` / `TravelDay` / `TravelSpot` / `HotelStay` / `SpotOption`
是**对前端的契约镜像**，与前端 `src/types/plan.ts` 一一对应 —— 改字段两边要一起改。

其中 `TravelDay.alternatives`（同一天的**其它走法**，目前只可能是飞机）与 `Transfer.mode`
是 2026-10-14 加机票时新增的，改这两个名字要同时改前端的类型、`api/plan.ts` 的假数据和页面渲染。
字段故意叫 `alternatives` 而不叫 `flight`：以后要加大巴、轮渡，加的是一类**备选走法**，
契约不用跟着改。

⚠️ `Persona` / `PersonaTrait` / `PersonaGuard` 也在 `plan` 包。2026-10-15 起它们**已是对外契约**：
`PlanChatData.persona` 透给前端、`PlanGenerateRequest.persona` 带回来、`PlanComposer` 渲染
【我对这个用户的判断】段（前端 `types/plan.ts` 已有镜像）。`DayReasons` 同一轮加进 `plan` 包，
产出 `TravelDay.why`（契约第 8 个字段）。

### 三个 Composer 的分工

| 类 | 干什么 | 温度为什么是 0.3 |
|---|---|---|
| `ChatComposer` | 一句话 → 画像增量 + 下一句追问 | 结构要稳（其实它更想要 0.7，见下） |
| `RetrievalPlanner` | 画像 → 该查什么（城市/类别/关键词） | 要稳定的结构，不要创意 |
| `PlanComposer` | 画像 + 候选 → 排好的行程 | 同上 |

> 已知取舍：三条调用共用一个 `ChatModel` 单例，而 `temperature` 是它的构建参数，只能给一个值。
> 现在共用 `0.3` —— 因为**三个里有两个怕随机，只有一个怕生硬**，按多数派决策。
> 哪天"对话语气太板"成为真实抱怨，再拆成两个 bean。

## 6. 几条值得知道的设计

**① 事实由代码保证，模型只负责措辞。**
模型看到的候选行是后端渲染的，它只能回编号。名称、价格、地址、购票链接、经纬度按编号回填。

**② 真实车次时刻提前查出、喂进 prompt，再加兜底检查。**
日期只由 `startDate + days` 决定，不需要等排程结果，所以车次查询可以提前。
配 `firstDayConflict` / `lastDayConflict` 两条纯函数兜底 ——
修掉过一个真 bug：行程排着"下午 15:00 珠江夜游"，而回程车早上 06:18 就开走了。

**③ 酒店与景点的距离由后端算好写进候选行，校验层再独立算一遍。**
prompt 里不给模型经纬度数字（让 LLM 比两串坐标是碰运气），而是把结果告诉它：
`H5 | 广州奥园喜来登酒店 | ... | 近：C3(1.7km) C2(2.0km) C5(2.4km)`。
同时 `PlanService.warnGeoConflicts` 独立算一遍兜底 ——
**prompt 是优化，代码才是保证。**

**④ 距离工具只有一份实现。**
`plan/Geo.java` 与前端 `distanceKm()` 用**同一套公式**（等距圆柱，半径 6371）。
两份实现不一致，前后端对同一对点的远近排序就会不同。

**⑤ 冲突不拦行程，只写进 `warnings`。**
不指望模型永不犯错，但它犯了，界面上一定有一句人话告诉用户
（"第 2 天晚上住华发国际公寓，第 3 天第一个点是情侣路，却在约 19.5 公里以外"）。

**⑥ 限流不是优化，是能不能用的前提。**
实测：并发 6 个 → 3 个 429；连续串行不间隔 → 后 3 个 451（风控）；
冷却 90 秒后串行 + 间隔 7 秒 → 全部成功。所以有 `min-gap-ms` 这道闸门。

**⑦ 机票只在「火车这条腿偏累」时才查，而且只作参考。**

- **触发条件是一个已定事实，不是猜的。** 火车查询返回「无直达」或「最快那班也超限」才补查一次航班；
  火车在 180 分钟内就**一次都不查**（`PlanServiceFlightTest` 钉住这一条）。
  一次 `/generate` 最多去/回各查一次 ⇒ 上游成本有上界，这也正是要保住 `min-gap-ms` 那条串行线的理由。
- ⚠️ **火车查询失败（`UPSTREAM_ERROR`）时不补查。** "不知道这条路多长"和"这条路太长"是两件事 ——
  前者去补查，要么白花一次额度，要么给出「这段路只有飞机」这种**假结论**。
- **两种载体并列展示，代码里不做「划不划算」的判断。** 票价随日期飘：同一条深圳→上海，
  12-10 最低 ¥610、11-17（深圳秋假）¥1510 —— **飘的幅度（2.5 倍）比两种载体之间的固定差距还大**。
  所以任何"机票更贵/更划算"的自动结论都是拿一个会飘的数字替用户做决定。
  界面只负责说清"票价是查询当时的"，并给个飞猪链接；选哪个由用户定。
- **`primary` / `alternatives` 是分开的**：`primary` 进 prompt（模型据此排首末日的时刻），
  `alternatives` **不进 prompt**（只给用户看）。火车有则火车当 `primary`（哪怕超限），火车没有才轮到飞机顶上。
- **两条取数事实，都是实测出来的（`--help` 不是契约）：**
  - `--total-duration-hour` 对机票会被上游 **400 拒绝**（`Argument not allowed: [totalDurationHour]`）——
    它在 `--help` 里列着，服务端不认。⇒ **机票的时长红线只能在本地判**，两种载体的查询条件必须分开拼。
  - `--journey-type 1` 对机票**有效**（只留直达）。不筛的话池子里混着 630 分钟的经停航班，
    而且**最便宜的那条往往是最慢的** —— 不筛时长，"最便宜"就是个陷阱。
- 机票的返回结构与火车**逐字同形**（`journeys[].segments[]` 字段名全一样），
  唯一差异是外层价格火车叫 `price`、机票叫 `ticketPrice`。所以一个 `FlyaiLeg` 同时服务两种载体
  （它原来叫 `FlyaiTrain`，那样命名是误导），载体由 `Transfer.mode` 带下去。
  `mode` **不参与任何判断**，只是把已经定下来的事实传到渲染层。

**⑧ 酒店要查两个档次，而且落选的那几家得摆出来（2026-10-14）。**

起因是一句用户反馈：**"档次似乎有点高，能不能多查几个酒店给候选"**。
把这句话拆成两件互不相干的事，是这一节的全部内容。

- **第一件：档位。** 原来的默认是 `--hotel-stars 4,5`，实测（上海，2026-11-17，同城同日）：

  | 参数 | 回来什么 | 价格 | 青旅/公寓 |
  |---|---|---|---|
  | 不带筛 | 9 条全**经济型** | ¥33~345 | **2 条** |
  | `3` | 10 条全**舒适型**（如家/维也纳/汉庭） | ¥103~314 | **0 条** |
  | `4` | **四星级/高档型**（假日/和颐） | ¥140~895 | 0 条 |
  | `4,5`（原默认） | **豪华型**（皇冠假日/JW万豪/索菲特） | ¥478~1277 | 0 条 |

  也就是说：当初加星级筛是为了**挡下限**（不带筛时 10 条里 6 条是青旅），代价却是把上限也锁死了 ——
  用户只看得到豪华档。所以默认改成 `3;4`：舒适档打底，四星/高档档作为"往上走"的选择。

- ⚠️ **`--hotel-stars` 一次只回一档，多值不是并集**（这是实测出来的，和 `--help` 的字面意思不一样）：

  ```
  "3,4" → 全"舒适型"    "2,3" → 全"舒适型"    "3,4,5" → 全"舒适型"
  "4"   → "四星级/高档型"                       "4,5"   → 全"豪华型"
  ```

  所以"让用户看到不同价位"**只能查两次**。配置里因此有了分号：
  **分号分组（查几次）、逗号传参（上游自己的语法）** —— `"3;4"` 是两次，`"4,5"` 是一次，
  老写法继续可用，两种语义也不会混。代价是一次 `/generate` 多一次上游调用（实测单次约 2.5 秒）。

- **没生效 / 有害的参数**，都实测过，记在这里免得有人再试：

  | 参数 | 结果 |
  |---|---|
  | `--sort price_asc` | **更糟**：¥22~¥70 一屏，10 条里 6 条是青旅/民宿。"最便宜的往往最差"和机票那边"最便宜的往往最慢"同一个陷阱 |
  | `--max-price N` | 只有上限没有下限，青旅照样混进来（实测 10 条里 3 条） |
  | `--hotel-types hotel` | 挡不住青旅 —— 青旅在它眼里也算 hotel |
  | `--sort rate_desc` | 与默认几乎一致，且 `rate` 字段恒为 null（上游不下发评分） |
  | `--hotel-stars` 不带日期查 | `star` 字段**全是 null** —— 星级的判据本身就没了 |

  最后一条是"必须带日期"的第二个理由：不带日期不止价格不准，连"这家是什么档"都拿不到。

- **第二件：备选。** 上游一次查回 10 家，模型只挑 1 家，**剩下 9 家原本直接丢掉** ——
  用户每天只看到一家酒店，甚至不知道那是从 10 家里挑的。
  这和机票 `alternatives` 是同一个思路（给模型看多少 ≠ 给用户多少可选，景点那边早就这么分了），
  但酒店这一层**不花任何额外查询**：那些酒店本来就在池子里。

  ⚠️ **取哪几家是"跨档轮转"，不是"最便宜的 3 家"** —— 这条是真跑一次才补上的：
  最初写成按价格取前 3，实测（广州→珠海）珠海最便宜的几家恰好全在舒适档，
  **四星档一家都没露出来**。那样第二档那次调用、那份 30 秒预算就是纯浪费，而且没有任何信号。
  所以规则是：按 `star` 分组、各组轮流出一家，取满 3 家，**再按价格升序展示**
  （选出谁 / 怎么摆是两件事）。单档位时它自然退化成"按价格取前 3"，不需要另写分支。

  另外两条：**每天都挂同一份**（"哪几天算连住"是前端 `mergeStays` 算的事，契约层不加能算出来的字段），
  以及**价格 null 排最后**（null 是"飞猪上没有可订房型"，不是免费）。

- **订房链接一直都在，只是前端没渲染。** `HotelCandidate.bookUrl` 是一条带上入离日期的飞猪路由短链，
  实测 302 落到 `…/rx-hotel-detail/pages/detail?shid=<这家酒店>&checkIn=…&checkOut=…` ——
  也就是**点开就是"你要去的那几天"的房态，能直接下单**。
  ⚠️ 但它每次请求都可能变（同一家酒店在不同查询里短码不一样），所以只能渲染、不能当标识。
  我们做的是搜索，下单在飞猪那边 —— 整个飞猪 CLI 只有 `search-*`，**没有任何下单命令**。

**⑨ persona：我们"推"出来的偏好，拿不出依据就活不下来（2026-10-14）。**

起因是一句想法：*"之前的画像更像标签，主要是用来规则过滤的。能不能形成一个对这个人偏好的看法，
记录为 persona，并记录我们是通过哪些对话觉得她有这些偏好的？"*

这句话顺手说出了一个真问题。现在 `TravelParams.preferences`（`["动物园"]`）和 `pace`（`"慢"`）
**只被消费、从没被理解过** —— 前者的作用是喂给 `RetrievalPlanner` 变成检索条件，
后者的作用是在 `PlanRules.spotsPerDay(pace)` 里决定每天排几个点。
用户说"我想有一个放松的旅行"，**大概率整句丢掉**。

- **persona 和 params 是两种东西，混在一起会出事。** 这是最要紧的一条：

  | | `TravelParams`（现有画像） | `Persona`（这轮加的） |
  |---|---|---|
  | 来源 | 用户**说过的** | 我们**推**的 |
  | 能不能核对 | 能 —— 他原话里有"9 天" | 不能 —— 只能回溯到依据 |
  | 错了会怎样 | 行程不合意，他会说"我说的是 4 天" | **他以为你懂他，其实你懂错了，而且不报错** |

  所以 persona 独立成 record，**不塞进 `TravelParams`**。两个具体理由：
  `mergedWith()` 的规则是「patch 里没答的字段一律保留原值」—— 这对事实是对的，
  对推论是灾难（上一轮推错的结论会因为"这轮模型没提"而被**永久粘住**）；
  而 `PlanComposer.renderParams()` 会把每个字段当**事实**渲染给模型看，
  推论混进去，模型下一轮就会把"我们猜的"当成"用户说的"继续加固。

- **合并规则反过来：同 key 覆盖，没提到的维度保留。** 方向是**增量**，不是整份替换 ——
  "模型这轮没输出 walking"和"用户撤回了怕走路"在 JSON 里长得一模一样（都是"没出现"）。
  两者分不开时选**保留**：保留错了只是一条过时偏好影响一次排程；
  丢掉错了是用户前面聊的全白聊，而且他看不见。"改主意"靠 **value 覆盖**表达
  （输出 `walking = 无所谓`），不靠缺失。

- **两道闸门，各管一半。** 结论（"放松" → "怕走路"）是语义跳跃，**没有任何机械方法能校验**，
  所以不校验结论；但**依据可以**：

  | 闸门 | 在哪 | 挡什么 |
  |---|---|---|
  | 维度闭集 | `plan/PersonaTrait.java` | 只能在这 5 个维度上推：`walking` 怕走路 / `crowd` 怕人多 / `rest` 要午睡 / `budget` 预算敏感 / `interest` 孩子的兴趣 |
  | 依据逐字回查 | `plan/PersonaGuard.java` | evidence 去空白标点后，必须在**用户说过的话**里逐字找得到；找不到整条丢弃 + 记账 |

  闭集不是"防模型写错"，是**把"什么算一个值得记住的偏好"从模型手里拿回来**：
  它只能在 5 个已经想清楚的维度上判断，想不出第 6 个，也就没机会过度推论。
  ⚠️ 诚实的边界：逐字回查只能证明**用户说过这句话**，不能证明**这句话推出了这个结论** ——
  "我想有个放松的旅行"→"不想折腾"是我们认可的推论，"我今天有点累"→"她体力很差"是过度推论，
  **机器眼里两者长得一模一样**。两道闸门各挡一半，谁也不能少。

  另外三条具体判断：
  - **只看 user 消息，不查 assistant。** 拿模型自己说过的话当依据等于**自证** ——
    它上一轮随口猜"看来您比较在意预算"，这一轮就能抄成 evidence，幻觉从此再也查不出来。
  - **value 只给方向，不做硬枚举。** `interest` 这类维度枚举不完，而硬枚举一旦遇上枚举不了的值，
    模型会挑**最近的那个**塞进去 —— 失败方式从"没记住"退化成"记错了"，比不记更糟。
  - **维度表和 `TravelParams` 不重叠。** `pace: "慢"` 已经在画像里了，persona 再存一条"节奏慢"
    就是**两处真相**，迟早打架。所以闭集只装画像那 8 个字段表达不了的、而且真会改变怎么排的东西。

- ⚠️ **已知代价，写下来免得以后当 bug 修**：
  - 用户分两句说的（"我想放松"+"我不爱走路"），模型把两句拼成一句当依据 → **会被挡下**。
    这是刻意的：拼接同时会放行"用户说了 A、也说了 B、所以推出 C"这类假因果。
    模型该做的是挑其中最能支撑结论的那一句。
  - 模型既不说"无所谓"、又不再输出那个维度时，旧判断会留着。要根治得给"明确作废"一个显式的词
    （像 `CandidateCodes.STAY_NONE` 那样）—— 那是另一层复杂度，本轮不做。
    用户侧还有一条不依赖模型的路：卡片上那条可以直接删。

- **接链路（2026-10-15 第二轮）**：第一轮只落了三个纯 static 类（`PersonaTrait` / `Persona` /
  `PersonaGuard`，48 个用例）+ 探针实测；第二轮把整条路接通 ——
  `ChatComposer.chat()` 多收一个 `currentPersona`、prompt 带【可以记的维度】和【已经推出来的判断】、
  输出 schema 加 `persona[]`，解析后**先过 `PersonaGuard.screen(messages)` 再合并**；
  `PlanChatData.persona` 透给前端；`PlanGenerateRequest.persona` 在生成时带回来；
  `PlanComposer` 渲染【我对这个用户的判断】段（每条带原话），并加一条硬性要求
  （理由里出现的数字必须来自候选行/车次行给过的事实）。
  端到端验收（`_probe/verify-l1-ui.mjs`，30/30）：假模型输出 persona → **真闸门逐字回查真对话**
  → 合并 → 契约 → 前端卡片；排程 prompt 里真的出现了那一段和用户原话。

  **每天那句理由（`TravelDay.why`）刻意不交给模型写**（`plan/DayReasons.java`，21 个用例）：
  理由里出现的任何可核实事实（到站时刻、当天跨度、点数、连住、发车时刻）必须来自本地算得出
  的东西 —— `Geo` 已经算过距离、`Legs` 已经算过车次、`PlanRules` 知道常规点数。
  persona 在这里只做一件事：**引用用户原话**，而且要判方向（`leansRelaxed` 排除
  "无所谓 / 不介意 / 不用"）—— 否则用户说过"体力很好"，会被引用成"今天排得轻松"的理由，
  **引用着真原话说假话**，界面上完全看不出来。上限 2 句、没有可说的事实就返回 null
  （缺坐标的天宁可不说，也不拿算得出的几段下结论）。
  另外三件**不做**：persona 不进检索条件（那会变成"推论 → 少查了几个类别"，错了看不见还多花额度）、
  persona 不覆盖硬规则（180 分钟上限、距离红线是产品的身份证）、不做跨会话记忆
  （项目没有用户体系，别为了它引入身份存储 —— 那是隐私问题，而收益只在第二次打开时才出现）。

- **实测（2026-10-15 · `_probe/persona-probe.sh`，8 组场景 × 2 遍）**：
  模型输出 7 条，**过闸门 7 条 · 被拦 0 条 · `evidence` 命中率 100%**，两遍逐字相同（含措辞）。

  这个数字**不能**读成"闸门没用"、更不能读成"可以拆掉"。8 组都是 2~5 轮的短对话 ——
  那是模型上下文最清爽、表现最好的情况。真用户聊十几轮之后，抄错行、把两句揉成一句的
  概率才开始上升，**那才是它存在的理由**。所以它的定位是**纵深防御**，不是日常过滤器：
  日常靠 prompt（这次 100% 命中恰恰是 prompt 写得够明确的功劳），prompt 一旦失守
  （换模型、换版本、上下文变长）由它兜住。成本是一次 `contains`。
  这和 `ChatComposer.sanitize` 那条注释是**同一个结构**：
  *prompt 说清楚（模型不该犯）是优化；代码兜住（犯了也没用）才是保证。*

  探针顺手抓出一个**只有真跑才看得见**的缺陷：`walking` 这个维度名叫「怕走路」，
  模型就只记"怕走路" —— 用户明说"我们一家体力都挺好，一天走两万步很轻松，不用考虑走不动"，
  它输出 `[]`，一条都不记。也就是"不怕走路"被读成了"没有这个特点"，而不是
  "这个维度上的一条判断"。prompt 里补一条（明确指出"用户说了相反方向也要记，
  无所谓 / 不介意 是一条有用的判断"）之后，立刻变成 `walking = 无所谓`。
  ⚠️ **闭集的维度名会带偏模型** —— 以后加维度时同一条要留意
  （"预算敏感"会不会只记"想省着花"、"怕人多"会不会只记"避开人多"）。

  四个诱饵**全部没上钩**：三个场景直接输出 `[]`（不硬凑）；"我今天上班有点累"没被推成
  "体力差"（不过度推论）；助手在历史里说过"按轻松一点、预算中等的方向安排"，
  模型没拿它当依据（不自证 —— 这正是"只查 user 消息"要防的那件事）；
  用户用口语说了 77 个字、其中没有一个标准词，模型**整句照抄、一个字没动**（不改写）。
  它也会**截子串**（从"我想带 6 岁的儿子去广州玩 3 天，这次我想安排得放松一点"里
  只抄"这次我想安排得放松一点"）—— 那是 prompt 明确允许的（"抄支撑结论的那一小段"）。
  顺带一个对前端有用的结论：**卡片上显示的依据通常就是用户原话的一小段**，可以直接展示。

## 9. 部署注意 / 已知限制

**部署时这个后端比一般 Web 服务多几件麻烦事**，先说清楚免得踩空：

1. **它要两个运行时**：JDK 21（跑 Jar）**和** Node.js（起子进程跑飞猪 CLI）。单一运行时镜像跑不起来。
2. **要三份凭据**：`DEEPSEEK_API_KEY` + 飞猪 `FLYAI_API_KEY` + `~/.flyai/device-id`。后两个在
   `~/.flyai/` 下，不在仓库里（这是对的，但意味着部署要单独注入）。
3. **新的 `device-id` 会不会被上游风控拦，未验证** —— 这是云部署最大的未知数。
   实测的限流阈值（429 / 451）都是在本机这台设备上测的。
4. `max-leg-minutes` / `hotel-stars` 这类产品约束的取值都有实测依据，
   写在配置注释里了，改之前先读注释。

**已知限制**：

- `/generate` 要 25~60 秒。现在报的是**真实的五步进度**（`GET /api/plan/progress/{runId}`，前端每秒轮询），
  但"步骤里面"还看不见：那 2~10 秒的检索查了几轮、是宽查还是补查，没有报出来。
- **机票只作参考，我们没有"哪种更划算"的判断。** 票价随日期飘的幅度比两种载体的固定差距还大（见第 6 节 ⑦），
  而门到门时间还要加上提前到机场和进城 —— 这两笔账都没算。界面上是把两种走法并排摆出来，选哪个由用户定。
- `HotelStay.rating` 实际上永远填不上 —— 飞猪酒店接口不带评分字段。要么删掉，要么显式显示"暂无评分"。
- 三条 LLM 调用共用一个温度（见第 5 节）。
- 多城市串联（如"广州+珠海"一次规划）没做。
