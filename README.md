# 童行 · 带娃旅游规划器

> **和 AI 聊几句，它去飞猪查真实的景点、酒店和城际车次，然后排出一份带娃真能跑得完的行程。**

`React 19` · `TypeScript` · `Vite 8` · `Tailwind 3` ｜ `Spring Boot 4.1` · `Java 21` · `LangChain4j` · `通义千问（百炼）`

> **在线体验：<http://114.132.233.6/>** —— 一次生成 30~60 秒（真的在查飞猪），建议先用「珠海 3 天，孩子 6 岁」试。

---

## 它解决什么问题

带娃出门，贵的不是机票，是**时间**：每天去哪儿、几点去、住哪、怎么去、回程车几点、孩子会不会累到崩溃 —— 这些排起来比订票本身费神得多。

而市面上的 AI 旅行助手大多在**编**：编一个不存在的营业时间，编一句"步行可达"其实隔着 40 公里。

这个项目的做法是反过来的：**事实由代码保证，模型只负责措辞。**

## 三条产品原则

**① 景点、酒店、城际班次（火车 / 机票）全部来自飞猪，不是模型编的。**
名称、价格、地址、经纬度、购票链接都是飞猪 FlyAI 接口的真实返回。模型拿到的是一份**候选清单**，它只能从里面挑，不能凭空造。

**② 模型的每句话都能溯源。**
行程页底部的「展开溯源」能看到这一趟**真实发出的查询命令**，和被规则层筛掉的候选 —— 成本是可见的。

**③ 代码才是保证，prompt 只是优化。**
模型偶尔仍会排出一段 24 公里的跨度。那没关系 —— 兜底校验会在界面上写一句人话告诉用户。**不指望它不犯错，但犯错时人一定看得见。**

## 架构

```
浏览器
  │  对话 / 生成行程
  ▼
前端 React（5173）
  │  /api   ← dev 时走 vite 代理，线上走 nginx 反代
  ▼
后端 Spring Boot（8003）
  ├─ ① 对话层   ChatService · ChatComposer    从闲聊里抠出画像（城市/天数/年龄/偏好…）
  ├─ ② 检索层   RetrievalService · LegService 调飞猪 CLI 查景点 / 酒店 / 城际车次（带限流与缓存）
  ├─ ③ 规则层   RuleChecker · PlanRules       白名单筛选：时长、星级、距离、营业状态
  ├─ ④ 编排层   PlanComposer（通义千问）      只能从候选里挑，产出逐天行程
  └─ ⑤ 校验层   PlanService.warnXxx           冲突兜底，写进 warnings 给人看
```

**接口**（统一响应 `{ code, message, data }`，HTTP 状态码**恒为 200**，业务失败用 `code !== 0` 表达）

| 方法 | 路径 | 请求 → 响应 data |
|---|---|---|
| POST | `/api/plan/chat` | `{ messages, currentParams, currentPersona }` → `{ reply, params, persona }` |
| POST | `/api/plan/generate` | `{ params, retrieval?, maxTicketPriceYuan?, persona }` → `{ summary, days[], warnings[], provenance, spotPool[] }`。带 `X-Run-Id` 请求头才记进度 |
| GET | `/api/plan/progress/{runId}` | — → `{ steps[{key,label,state,tookMs}], elapsedMs, finished, ok }`（生成期间的真实分段耗时，见设计 7；未知 runId 回 `null` 而不是空进度） |

`currentPersona` / `persona` 是**推论**、`params` 是**事实**，两者刻意分开存（见设计 10）；不传就是空，不影响调用。

字段命名统一 camelCase，前后端**逐字一致** —— 写成 `child_age` 不会报错，只会永远是 `undefined`。

## 几个值得一看的设计

### 1. 让模型「只能挑，不能编」

模型看到的候选行是**代码渲染**出来的，不是它自己检索的：

```
C3 | 广州长隆野生动物世界 | 主题乐园 | ¥300 | 近：H5(1.7km)
H5 | 广州奥园喜来登酒店 | 高档型 | ¥688/晚 | 近：C3(1.7km) C2(2.0km) C5(2.4km)
```

它输出的每一项都要带编号（`C3` / `H5`），后端**按编号回填**名称、价格、地址、链接和经纬度。
于是"编一个不存在的景点"在结构上就做不到 —— 编号对不上，那一条直接被丢掉并记进"被筛掉的候选"。

### 2. 把真实车次时刻**提前**查出来，喂进 prompt

一个真实修过的 bug：排程模型不知道车次时刻，于是第 5 天下午 15:00 还排着夜游，而回程车 06:18 就开走了。

根因不是 prompt 写得不好，是**它压根没拿到时刻**。修法是把车次查询**提前到排程之前**（日期只由出发日 + 天数决定，不用等排程结果），把真实时刻写进 prompt，再配两条兜底检查（首日首点不得早于到站后 1 小时；末日不得晚于发车前 3 小时）。

顺带一个更隐蔽的：回程时段的判据原本**只有上界没有下界**，于是"最快的一班"（29 分钟的 06:18 首班车）一路绿灯。而它在另一个城市"碰巧是对的"（珠海最快的是 18:13 晚班车）—— 靠数据分布撞对的规则不算规则。

### 3. 一段路「太长」，不该被当成「没有」

一个真实修过的 bug：用户要去上海，生成出来的行程里**一行车票信息都没有**，注意事项写着
「深圳 到 上海 在 180 分钟内没有直达车次」。

这句话读起来是个确定的结论，而它是**假的** —— 深圳 → 上海的高铁是存在的，约 6.5 小时。

根因在取数、不在界面：查车次时那个"最多几小时"的**上游筛选参数**被写成了那条上限本身
（180 分钟 → 3 小时）。上游按时长筛完返回 `{"status":1,"message":"行程时长过滤结果为空"}`，
而我们把"这个窗口内没有"读成了"这段路没有走法"。
**一条真能走的路线就这样被静默拿掉了** —— 不报错、不告警，只是行程里少了一整行。

修法两步，每一步都对着一个具体的错：

- **粗筛窗口和那条上限解耦。** 窗口放宽到 12 小时，红线仍然只留在本地那条
  `minutes <= maxLegMinutes()` 上。这样"最快的一班也超限"的路依然拿得到候选 ——
  否则我们连"它要多久"都说不出来。
- **超限就如实说，而且把车留下。** 结果多一个 `overLimit` 标记，警告变成
  「最快的一班也要 6 小时 34 分（高铁G270 07:43 深圳北 → 14:17 上海虹桥）—— 超过单段 180 分钟这条上限」。

第二条才是关键：**那条上限是我们替他设的默认，不是他的原话。** 把车藏起来，
他连"要坐多久"都看不到，更谈不上决定接不接受。这和"一条班次都不满足时段就退回第一条"
是同一条原则 —— **给一份真实但不理想的东西，永远好过把选择拿走。**

（`_probe/verify-leg-overlimit.mjs` 盯的就是它：去程/回程**都有**车票、警告说的是"太长"而不是"没有"，
而且警告里那个耗时数字脚本会自己复算一遍。）

**这个修复顺带暴露了另一个更隐蔽的。** 回程那个时段窗口原来只比 `LocalTime`，
于是"20:15 发车、**次日** 07:03 到"的过夜车被读成"早上 7 点到家"，完美落在"别太晚到家"那条上界之内 ——
一趟 **10 小时 48 分的夜车**就此被选成了"最合适的回程"，而"带娃坐一整夜"它一个字都不会提。

判跨午夜必须比**日期**。`Transfer.arrDateTime` 早就带着日期了（那个字段存在的全部理由就是这个），
只是 `pick` 这条路上没人用它。**同一个形状的错：规则对，取值方式错。**

### 4. 距离：后端算好告诉它，再兜底校验

`C3(1.7km)` 那种标注不是让模型去算经纬度（LLM 算这个是碰运气），而是**后端把距离算好、把答案告诉它**。同时校验层独立再算一遍：当天相邻两点跨度、以及"昨晚住处 ↔ 今天第一个点"超阈值就写进 warnings。

不指望它不犯 —— 实测模型仍排出过 24 公里的跨度。关键是那一刻界面上有一句话告诉用户。

### 5. 「换一个」是稀疏覆盖，不是改行程

用户点「换一个」时，**不去改** `plan.days`，而是往一张 `Record<"day:index", SpotOption>` 表里塞一条覆盖，渲染时才叠加：

```ts
const days = applySwaps(plan.days, swaps)
```

好处是撤销＝删一个键，重新生成＝换一份 plan + 清空表，两件事互不干扰。后端产 **fact**，用户产 **edit**，界面只负责叠加。

两个刻意的细节：**时间保留**（用户换的是"去哪儿"，不是"几点去"）；**tips 清空**（模型那句建议是针对原来那个点的位置写的，搬过去就是"读起来完全正常、实际纯属编造"的话 —— 这正是这个产品最该怕的错）。

### 6. 探针：怎么证明验证本身没在自欺欺人

`_probe/` 下 42 支脚本，是"怎么验收一个 LLM 应用"的完整记录。核心不是"跑通了"，而是三件事：

- **独立复算** —— 例如验距离标注：自己从飞猪原始缓存读坐标、自己算全部候选距离、自己取最近三个，再和日志里渲染出来的**逐个对**（编号 + 公里数）。只断言"日志里有 `近：C3(1.7km)`"是**形状验证**：一个乱序的、取最远三个的实现照样能过。
- **双向对账** —— 有冲突必须有警告，**没冲突必须没有警告**。误报比漏报更可怕：警告一多，真问题就被淹了。
- **反证记录** —— 每条重要断言旁边留着"我怎么确认它真的会红"：临时改坏代码，确认测试/探针报错，再改回来。带着反证的绿灯才算绿灯。

### 7. 生成那几十秒：报真进度，不报百分比

`/generate` 一次要 25~60 秒。之前这段时间界面上只有一句「正在生成（要几十秒）…」——
用户没有任何办法判断系统是在干活，还是已经卡死了。

现在的做法是把后端**真实走过的五段**报出来，前端一边等一边每秒问一次：

```
✓ 查城际车次              4.2 秒
✓ 规划这次要查什么        15.1 秒
● 查飞猪的景点和酒店      进行中
○ 挑景点、排日程
○ 校验行程
```

三个刻意的取舍：

- **没有百分比，也没有会走到头的进度条。** 五段耗时完全不可预测（模型那两段在 10~30 秒之间浮动），
  任何"已完成 68%"都只能靠编 —— 而"看起来很像真的、其实是编的"正是这个产品最该怕的错。
  界面上那条扫光只表达"在动，但不知道还要多久"。
- **耗时是真量出来的。** 每一步的**开始时刻**被记下来，相邻两步相减就是真实花费。
  反过来说：如果五步耗时看起来差不多，那就是拿总时长均摊的 —— 探针里专门有一条断言盯着这件事
  （`_probe/verify-progress-api.mjs`：最长的步和最短的步必须差出 200 毫秒以上）。
- **打点是旁路。** `runId` 在后端编排里只以 `progress.mark(runId, …)` 的形式出现，
  不参与任何判断、不进任何返回值。哪天有人让流程"根据进度做点别的"，这条线就断了 ——
  那时它不再是观测，而是会改变结果的东西。

为什么不流式（SSE）？最初是**部署环境决定的**：这条产品先要能跑在任意反向代理后面（当时的方案是内网穿透，
而 Cloudflare 免费隧道不支持 SSE，流式会在最要命的那一刻断掉）。后来上了腾讯云轻量 + nginx，SSE 其实可行了，
但仍然保留轮询 —— 它不依赖 `proxy_buffering` 之类的调参，换到任何托管平台上都不会因为一段配置而静默失效，
代价只是进度最多晚 1 秒。

### 8. 一段路偏累的时候，把飞机也摆出来（但不说哪种更划算）

`max-leg-minutes` 那条红线是替"带娃"设的，不是替"省钱"设的。所以当一段路**只有超限的走法**时，
"把车藏起来"是错的，而"告诉他还有飞机"是对的：

- **触发条件是已定事实，不是猜的。** 火车查询返回「无直达」或「最快那班也超限」，
  才补查一次航班；火车在 180 分钟内就**一次都不查**（`PlanServiceFlightTest` 钉住这四条）。
- **火车查询失败时不补查。** "不知道这条路多长"和"这条路太长"是两件事 ——
  前者去补查，要么白花一次上游额度，要么给出「这段路只有飞机」这种**假结论**。
- **只作参考，不做"划不划算"的判断。** 因为这个判断做不了：票价随日期飘，
  同一条深圳→上海，**12-10 最低 ¥610、11-17（深圳秋假）¥1510** ——
  飘的幅度（2.5 倍）**比两种载体之间的固定差距还大**。任何自动结论都是拿一个会飘的数字替用户做决定。
  界面只写清"票价是查询当时的"，并给个飞猪链接，选哪个由用户定。
- **主选进 prompt，备选不进。** 模型要按真实时刻排首末日的行程，所以它只该看到那一条 `primary`
  （火车有则火车当主选，哪怕超限；火车没有才轮到飞机顶上）。备选纯粹是给用户看的。

两条取数事实都是**实测**出来的，而且其中一条直接推翻了文档：

- `--total-duration-hour` 对机票会被上游 **400 拒绝**（`Argument not allowed: [totalDurationHour]`）——
  它在 `--help` 里明明列着。**help 不是契约。** 于是机票的时长红线只能在本地判。
- `--journey-type 1` 对机票有效（只留直达）。不筛的话池子里混着 630 分钟的经停航班，
  而且**最便宜的那条往往是最慢的** —— 不筛时长，"最便宜"是个陷阱。

一个反直觉的实测结论：**机票贵不贵完全取决于日期。** 12-10 那天机票 ¥610，
比高铁白天最快的 ¥848 **又便宜又快**（2 小时 vs 6.5 小时）；同一个航班在 11-17 要 ¥1510。
所以"机票通常更贵"是错的，正确的话是"机票的价格是会飘的，所以它只能作参考"。

⚠️ 这次比价里还踩过一个坑，值得记：高铁那个"最低 ¥668"是 G896 **20:26→次日 06:58 的夜车**（632 分钟），
拿它当"高铁 668 元 6 小时"去对标机票是错的。**比价必须比同类项（白天的车/机）。**

（`_probe/verify-flight-api.mjs` 36 项盯着它：主选还是火车、备选是飞机、同一天、
机票命令里**没有** `--total-duration-hour` 而有 `--journey-type 1`、短腿一次航班都不查，
最后还用假模型 + 真上游**独立复算**了一遍航班号/耗时/票价/时刻。）

### 9. 酒店：档次是产品判断，"多给几家"是不该丢掉那 9 家

起因是一句用户反馈 —— **"档次似乎有点高，能不能多查几个酒店给候选"**。
这句话里其实是两件互不相干的事，拆开看才是对的。

**第一件：档位。** 原来的默认是 4,5 星，实测（上海，同城同日）回来的全是
**皇冠假日 / JW万豪 / 索菲特，¥478~¥1277** —— 当初加星级筛是为了**挡下限**
（不带筛时 10 条里 6 条是青旅/日租公寓），代价却是把上限也一起锁死了。

| 参数 | 回来什么 | 价格 | 青旅 |
|---|---|---|---|
| 不带筛 | 全**经济型** | ¥33~345 | **2 条** |
| `3` | 全**舒适型**（如家/维也纳） | ¥103~314 | 0 条 |
| `4` | **四星/高档型**（假日/和颐） | ¥140~895 | 0 条 |
| `4,5`（原默认） | **豪华型** | ¥478~1277 | 0 条 |

⚠️ 关键的一条是实测出来的、和 `--help` 字面意思相反的事：**`--hotel-stars` 一次只回一档，
多值不是并集**（`"3,4"` / `"2,3"` / `"3,4,5"` 回来都是清一色"舒适型"）。
所以"让用户看到不同价位"**只能查两次**。配置里因此有了分号：
`"3;4"` = 查两次，`"4,5"` = 查一次，两种语义不会混。

**第二件：备选。** 上游一次查回 10 家，模型只挑 1 家，**剩下 9 家原本直接丢掉** ——
用户每天只看到一家酒店，甚至不知道那是从 10 家里挑的。这和机票的 `alternatives` 是同一个思路
（**给模型看多少 ≠ 给用户多少可选**，景点那边早就这么分了），而且酒店这一层**不花任何额外查询**。

⚠️ 但"取哪几家"有个坑，是真跑一次才补上的：最初写成"按价格取前 3"，实测（广州→珠海）
珠海最便宜的几家恰好全在舒适档，**四星档一家都没露出来** ——
那样第二档那次调用、那份 30 秒预算就是纯浪费，而且没有任何信号。所以改成
**按档位分组、各组轮流出一家，取满 3 家，再按价格升序展示**（选出谁 / 怎么摆是两件事）。

顺带修掉一个一直存在的洞：`bookUrl` 后端一直在发，**前端一个字都没渲染** ——
也就是说整份行程里唯一能直接把用户带到酒店的那条路一直是断的（交通行却有"去飞猪看这趟车"）。

关于"飞猪能不能订酒店"：**能订，但只能跳转过去订。**
每家酒店的 `bookUrl` 是一条带上入离日期的路由短链，实测 302 落到
`…/rx-hotel-detail/pages/detail?shid=<这家酒店>&checkIn=…&checkOut=…` ——
**点开就是"你要去的那几天"的房态**。而整个飞猪 CLI 只有 `search-*`，**没有任何下单命令**，
所以我们能做的是搜索 + 跳转，下单在飞猪那边。

（`_probe/verify-hotel-api.mjs` 31 项盯着它：两档各查一次且都带入离日期、
备选每天都有、**跨档**、按价格升序、不含主选、每家都有链接、独立复算名字/价格/档次词逐字相同。）

### 10. persona：只记我们想清楚的 4 件事，而且每条都得拿得出原话

起因是一句想法 —— **"之前的画像更像标签，主要是用来规则过滤的。能不能形成一个对这个人偏好的看法？"**

这个诊断是对的。`preferences: ["动物园"]` 和 `pace: "慢"` 现在**只被消费、从没被理解过**：
前者变成一次检索条件，后者在 `spotsPerDay(pace)` 里决定每天排几个点。
用户说"我想有一个放松的旅行"，**大概率整句丢掉**。

但 persona 是**推论**，和画像是两种东西 —— 这才是重点：

| | 画像（现有） | persona |
|---|---|---|
| 来源 | 用户**说过的** | 我们**推**的 |
| 错了会怎样 | 他会说"我说的是 4 天" | **他以为你懂他，其实你懂错了，而且不报错** |

所以它得先过两道闸门：

1. **维度是闭集，只有 4 个** —— 怕走路 / 怕人多 / 要午睡 / 预算敏感。
   这不是防模型写错，是**把"什么算一个值得记住的偏好"从它手里拿回来**：
   它只能在已经想清楚的那几件事上判断，想不出第 5 个，也就没机会过度推论。
   （刻意**不**放"节奏慢"这类 —— 那已经在画像里了，重复存就是两处真相。
     "孩子的兴趣"原本在这里，2026-10-15 移出去了：它是**多值**的，而这个闭集是**单值**的
     —— 用户说"喜欢海洋馆，动物园"，画像记下两个，persona 只能留一个。兴趣本来就归 `preferences`。）
2. **每条都得拿得出依据，而且那句话要逐字在用户说过的话里找得到。**
   这一下堵死的是最危险的那种幻觉：**编一句用户没说过的话来当证据** ——
   它带着"证据"上市，比真的还像真的。

⚠️ 诚实的边界：逐字回查只能证明**用户说过这句话**，不能证明**这句话推出了这个结论** ——
"我想放松"→"不想折腾"是认可的推论，"我今天有点累"→"她体力很差"是过度推论，
**机器眼里这两者长得一模一样**。两道闸门各挡一半，谁也不能少。

**两段做完了（2026-10-15）**。第一段只落闸门本身（`PersonaTrait` / `Persona` / `PersonaGuard`
三个纯 static 类 + 48 个用例），先跑了一次真实对话（`_probe/persona-probe.sh`，8 组场景 × 2 遍）：
模型输出 7 条，**过闸门 7 条 · 被拦 0 条 · 依据命中率 100%**，两遍逐字相同。

这个数字**不能**读成"闸门没用" —— 8 组都是 2~5 轮的短对话，那是模型表现最好的情况；
真用户聊十几轮之后抄错行、把两句揉成一句的概率才开始上升，**那才是它存在的理由**。
所以定位是**纵深防御**：日常靠 prompt，prompt 失守时由它兜住（和 `ChatComposer.sanitize` 同一条结构）。

探针倒是抓出一个**只有真跑才看得见**的缺陷：维度名叫「怕走路」，模型就只记"怕走路" ——
用户明说"体力好，不用考虑走不动"，它输出 `[]`。**闭集的维度名会带偏模型。**
prompt 补一条（"说了相反方向也要记"）之后立刻变成 `walking = 无所谓`。
四个诱饵（不硬凑 / 不过度推论 / 不自证 / 不改写）则全部没上钩。

第二段把链路接通：对话端 `ChatComposer` 让模型顺带输出 `persona[]`、**先过真闸门再合并**、
`PlanChatData.persona` 透给前端（「我这样理解你」卡片，每条挂用户原话）；生成端前端把 persona
带回来，`PlanComposer` 渲染【我对这个用户的判断】段。**每天那句"为什么这么排"（`TravelDay.why`）
刻意不交给模型写**（`plan/DayReasons.java`）：理由里的数字（到站时刻、当天跨度、点数、连住）
必须来自本地算得出的东西，persona 只用来**引用用户原话**，而且要判方向 —— 用户说过"体力很好"，
绝不能被引用成"今天排得轻松"的理由（那等于引用着真原话说假话，界面上看不出来）。
端到端（`_probe/verify-l1-ui.mjs` 30/30）：一句话带偏好的对话 → 卡片亮出来 →
排程 prompt 里真的出现那一段 → 第 1 天的理由是完整组合句
（到站时刻 + 用户原话 + 本地算的 0.7 公里）。

## 已知限制

- **不接第三方攻略。** 小红书之类的内容源**没有接入**，数据源就是飞猪。行程里的"游玩建议"是模型写的，景点/酒店/车次是飞猪的 —— 界面上这两类信息应当被区分看待。
- **只收孩子年龄，不收大人数量。** 界面上的价格全部是**单价**（票价、房价），没有任何总价汇总，所以大人几个不影响输出；而"收了却不影响输出的字段"等于骗用户回答一个问题。带几个孩子会影响排程（数量 → 每天几个点、住几间房另算），所以只收年龄、并且按**最小的那个**算体力。
- **没有持久化。** 行程不落库，刷新即失，也没有历史记录。
- **上游有额度。** 飞猪接口实测会在连续调用时返回 429/451，所以检索层带间隔、缓存和预跑。演示前建议先跑 `_probe/prerun.mjs` 把结果落到磁盘。
- **前端没有单元测试**（后端 382 个单测 / 27 个测试类）。前端靠 `_probe/verify-*-ui.mjs` 在真实浏览器里验收。
- **机票只作参考，我们没有"哪种更划算"的判断**（见设计 8）：票价随日期飘的幅度比两种载体本身的差距还大，
  门到门时间也没算进去（提前到机场、落地进城）。界面上是把两种走法并排摆出来，选哪个由用户定。
- **生成期间只有"步"可见，"步里面"还看不见。** 现在能看到走到哪一步了（见设计 7），
  但"检索"那 2~10 秒里查了几轮、是宽查还是补查，还没有报出来。
