# 童行 · 带娃旅游规划器

> **和 AI 聊几句，它去飞猪查真实的景点、酒店和城际车次，然后排出一份带娃真能跑得完的行程。**

`React 19` · `TypeScript` · `Vite 8` · `Tailwind 3` ｜ `Spring Boot 4.1` · `Java 21` · `LangChain4j` · `DeepSeek`

---

## 它解决什么问题

带娃出门，贵的不是机票，是**时间**：每天去哪儿、几点去、住哪、怎么去、回程车几点、孩子会不会累到崩溃 —— 这些排起来比订票本身费神得多。

而市面上的 AI 旅行助手大多在**编**：编一个不存在的营业时间，编一句"步行可达"其实隔着 40 公里。

这个项目的做法是反过来的：**事实由代码保证，模型只负责措辞。**

## 三条产品原则

**① 景点、酒店、车次全部来自飞猪，不是模型编的。**
名称、价格、地址、经纬度、购票链接都是飞猪 FlyAI 接口的真实返回。模型拿到的是一份**候选清单**，它只能从里面挑，不能凭空造。

**② 模型的每句话都能溯源。**
行程页底部的「展开溯源」能看到这一趟**真实发出的查询命令**，和被规则层筛掉的候选 —— 成本是可见的。

**③ 代码才是保证，prompt 只是优化。**
模型偶尔仍会排出一段 24 公里的跨度。那没关系 —— 兜底校验会在界面上写一句人话告诉用户。**不指望它不犯错，但犯错时人一定看得见。**

## 快速开始

### 前置

| | 要求 |
|---|---|
| Node | ≥ 20.19 或 ≥ 22.12（Vite 8 的硬要求） |
| Java | 21 |
| Maven | 3.9+ |
| 飞猪 CLI | `npm i -g @fly-ai/flyai-cli`（黑客松提供的取数工具） |
| DeepSeek | 一个 API Key |

### 两个环境变量（都必须配）

```bash
export DEEPSEEK_API_KEY=sk-xxxx        # PowerShell: $env:DEEPSEEK_API_KEY="sk-xxxx"

# 飞猪 CLI 的 bundle 路径。不知道在哪就 `npm root -g`
export FLYAI_CLI_PATH="$(npm root -g)/@fly-ai/flyai-cli/dist/flyai-bundle.cjs"
# Windows: $env:FLYAI_CLI_PATH="$env:APPDATA\npm\node_modules\@fly-ai\flyai-cli\dist\flyai-bundle.cjs"
```

⚠️ 这两个**故意都不留默认值**。写进仓库的密钥等于泄露；写进仓库的本机路径等于换台机器就跑不起来。少配一个，后端会在**启动时**就报一句人话，而不是等你点了"生成"才失败。

### 启动

```bash
# 后端 → http://localhost:8003
cd backend && mvn spring-boot:run

# 前端 → http://localhost:5173（另开一个终端）
cd frontend && npm install && npm run dev
```

打开 <http://localhost:5173/>，说一句「想带孩子去珠海玩 3 天，孩子 6 岁」。

> **后端没起来也能看界面。** `VITE_USE_MOCK=true npm run dev` 会用假数据跑通全流程 ——
> 界面上会有黄色横幅，且假行程的名字都带「（假数据）」。降级刻意做得很显眼：
> 静默降级会让用户拿着一份编出来的行程去订酒店。

## 架构

```
浏览器
  │  对话 / 生成行程
  ▼
前端 React（5173）
  │  /api   ← dev 时走 vite 代理，线上走 nginx 反代
  ▼
后端 Spring Boot（8003）
  ├─ ① 对话层   ChatService · ChatComposer    从闲聊里抠出画像（城市/天数/年龄/偏好…）
  ├─ ② 检索层   RetrievalService · LegService 调飞猪 CLI 查景点 / 酒店 / 城际车次（带限流与缓存）
  ├─ ③ 规则层   RuleChecker · PlanRules       白名单筛选：时长、星级、距离、营业状态
  ├─ ④ 编排层   PlanComposer（DeepSeek）      只能从候选里挑，产出逐天行程
  └─ ⑤ 校验层   PlanService.warnXxx           冲突兜底，写进 warnings 给人看
```

**接口**（统一响应 `{ code, message, data }`，HTTP 状态码**恒为 200**，业务失败用 `code !== 0` 表达）

| 方法 | 路径 | 请求 → 响应 data |
|---|---|---|
| POST | `/api/plan/chat` | `{ messages, currentParams }` → `{ reply, params }` |
| POST | `/api/plan/generate` | `{ params }` → `{ summary, days[], warnings[], provenance, spotPool[] }` |

字段命名统一 camelCase，前后端**逐字一致** —— 写成 `child_age` 不会报错，只会永远是 `undefined`。

## 几个值得一看的设计

### 1. 让模型「只能挑，不能编」

模型看到的候选行是**代码渲染**出来的，不是它自己检索的：

```
C3 | 广州长隆野生动物世界 | 主题乐园 | ¥300 | 近：H5(1.7km)
H5 | 广州奥园喜来登酒店 | 高档型 | ¥688/晚 | 近：C3(1.7km) C2(2.0km) C5(2.4km)
```

它输出的每一项都要带编号（`C3` / `H5`），后端**按编号回填**名称、价格、地址、链接和经纬度。
于是"编一个不存在的景点"在结构上就做不到 —— 编号对不上，那一条直接被丢掉并记进"被筛掉的候选"。

### 2. 把真实车次时刻**提前**查出来，喂进 prompt

一个真实修过的 bug：排程模型不知道车次时刻，于是第 5 天下午 15:00 还排着夜游，而回程车 06:18 就开走了。

根因不是 prompt 写得不好，是**它压根没拿到时刻**。修法是把车次查询**提前到排程之前**（日期只由出发日 + 天数决定，不用等排程结果），把真实时刻写进 prompt，再配两条兜底检查（首日首点不得早于到站后 1 小时；末日不得晚于发车前 3 小时）。

顺带一个更隐蔽的：回程时段的判据原本**只有上界没有下界**，于是"最快的一班"（29 分钟的 06:18 首班车）一路绿灯。而它在另一个城市"碰巧是对的"（珠海最快的是 18:13 晚班车）—— 靠数据分布撞对的规则不算规则。

### 3. 一段路「太长」，不该被当成「没有」

一个真实修过的 bug：用户要去上海，生成出来的行程里**一行车票信息都没有**，注意事项写着
「深圳 到 上海 在 180 分钟内没有直达车次」。

这句话读起来是个确定的结论，而它是**假的** —— 深圳 → 上海的高铁是存在的，约 6.5 小时。

根因在取数、不在界面：查车次时那个"最多几小时"的**上游筛选参数**被写成了那条上限本身
（180 分钟 → 3 小时）。上游按时长筛完返回 `{"status":1,"message":"行程时长过滤结果为空"}`，
而我们把"这个窗口内没有"读成了"这段路没有走法"。
**一条真能走的路线就这样被静默拿掉了** —— 不报错、不告警，只是行程里少了一整行。

修法两步，每一步都对着一个具体的错：

- **粗筛窗口和那条上限解耦。** 窗口放宽到 12 小时，红线仍然只留在本地那条
  `minutes <= maxLegMinutes()` 上。这样"最快的一班也超限"的路依然拿得到候选 ——
  否则我们连"它要多久"都说不出来。
- **超限就如实说，而且把车留下。** 结果多一个 `overLimit` 标记，警告变成
  「最快的一班也要 6 小时 34 分（高铁G270 07:43 深圳北 → 14:17 上海虹桥）—— 超过单段 180 分钟这条上限」。

第二条才是关键：**那条上限是我们替他设的默认，不是他的原话。** 把车藏起来，
他连"要坐多久"都看不到，更谈不上决定接不接受。这和"一条班次都不满足时段就退回第一条"
是同一条原则 —— **给一份真实但不理想的东西，永远好过把选择拿走。**

（`_probe/verify-leg-overlimit.mjs` 盯的就是它：去程/回程**都有**车票、警告说的是"太长"而不是"没有"，
而且警告里那个耗时数字脚本会自己复算一遍。）

**这个修复顺带暴露了另一个更隐蔽的。** 回程那个时段窗口原来只比 `LocalTime`，
于是"20:15 发车、**次日** 07:03 到"的过夜车被读成"早上 7 点到家"，完美落在"别太晚到家"那条上界之内 ——
一趟 **10 小时 48 分的夜车**就此被选成了"最合适的回程"，而"带娃坐一整夜"它一个字都不会提。

判跨午夜必须比**日期**。`Transfer.arrDateTime` 早就带着日期了（那个字段存在的全部理由就是这个），
只是 `pick` 这条路上没人用它。**同一个形状的错：规则对，取值方式错。**

### 4. 距离：后端算好告诉它，再兜底校验

`C3(1.7km)` 那种标注不是让模型去算经纬度（LLM 算这个是碰运气），而是**后端把距离算好、把答案告诉它**。同时校验层独立再算一遍：当天相邻两点跨度、以及"昨晚住处 ↔ 今天第一个点"超阈值就写进 warnings。

不指望它不犯 —— 实测模型仍排出过 24 公里的跨度。关键是那一刻界面上有一句话告诉用户。

### 5. 「换一个」是稀疏覆盖，不是改行程

用户点「换一个」时，**不去改** `plan.days`，而是往一张 `Record<"day:index", SpotOption>` 表里塞一条覆盖，渲染时才叠加：

```ts
const days = applySwaps(plan.days, swaps)
```

好处是撤销＝删一个键，重新生成＝换一份 plan + 清空表，两件事互不干扰。后端产 **fact**，用户产 **edit**，界面只负责叠加。

两个刻意的细节：**时间保留**（用户换的是"去哪儿"，不是"几点去"）；**tips 清空**（模型那句建议是针对原来那个点的位置写的，搬过去就是"读起来完全正常、实际纯属编造"的话 —— 这正是这个产品最该怕的错）。

### 6. 探针：怎么证明验证本身没在自欺欺人

`_probe/` 下 35 支脚本，是"怎么验收一个 LLM 应用"的完整记录。核心不是"跑通了"，而是三件事：

- **独立复算** —— 例如验距离标注：自己从飞猪原始缓存读坐标、自己算全部候选距离、自己取最近三个，再和日志里渲染出来的**逐个对**（编号 + 公里数）。只断言"日志里有 `近：C3(1.7km)`"是**形状验证**：一个乱序的、取最远三个的实现照样能过。
- **双向对账** —— 有冲突必须有警告，**没冲突必须没有警告**。误报比漏报更可怕：警告一多，真问题就被淹了。
- **反证记录** —— 每条重要断言旁边留着"我怎么确认它真的会红"：临时改坏代码，确认测试/探针报错，再改回来。带着反证的绿灯才算绿灯。

### 7. 生成那几十秒：报真进度，不报百分比

`/generate` 一次要 25~60 秒。之前这段时间界面上只有一句「正在生成（要几十秒）…」——
用户没有任何办法判断系统是在干活，还是已经卡死了。

现在的做法是把后端**真实走过的五段**报出来，前端一边等一边每秒问一次：

```
✓ 查城际车次              4.2 秒
✓ 规划这次要查什么        15.1 秒
● 查飞猪的景点和酒店      进行中
○ 挑景点、排日程
○ 校验行程
```

三个刻意的取舍：

- **没有百分比，也没有会走到头的进度条。** 五段耗时完全不可预测（模型那两段在 10~30 秒之间浮动），
  任何"已完成 68%"都只能靠编 —— 而"看起来很像真的、其实是编的"正是这个产品最该怕的错。
  界面上那条扫光只表达"在动，但不知道还要多久"。
- **耗时是真量出来的。** 每一步的**开始时刻**被记下来，相邻两步相减就是真实花费。
  反过来说：如果五步耗时看起来差不多，那就是拿总时长均摊的 —— 探针里专门有一条断言盯着这件事
  （`_probe/verify-progress-api.mjs`：最长的步和最短的步必须差出 200 毫秒以上）。
- **打点是旁路。** `runId` 在后端编排里只以 `progress.mark(runId, …)` 的形式出现，
  不参与任何判断、不进任何返回值。哪天有人让流程"根据进度做点别的"，这条线就断了 ——
  那时它不再是观测，而是会改变结果的东西。

为什么不流式（SSE）？流式看起来更"正"，但这条产品要跑在**内网穿透**上，
而 Cloudflare 免费隧道**不支持 SSE** —— 流式会在最要命的那一刻断掉。
轮询在任何代理上都稳，代价只是进度最多晚 1 秒。

## 已知限制

- **不接第三方攻略。** 小红书之类的内容源**没有接入**，数据源就是飞猪。行程里的"游玩建议"是模型写的，景点/酒店/车次是飞猪的 —— 界面上这两类信息应当被区分看待。
- **没有持久化。** 行程不落库，刷新即失，也没有历史记录。
- **上游有额度。** 飞猪接口实测会在连续调用时返回 429/451，所以检索层带间隔、缓存和预跑。演示前建议先跑 `_probe/prerun.mjs` 把结果落到磁盘。
- **前端没有单元测试**（后端 247 个单测）。前端靠 `_probe/verify-*-ui.mjs` 在真实浏览器里验收。
- **生成期间只有"步"可见，"步里面"还看不见。** 现在能看到走到哪一步了（见设计 6），
  但"检索"那 2~10 秒里查了几轮、是宽查还是补查，还没有报出来。
